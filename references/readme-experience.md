# Reader experience in persona READMEs

Read this when authoring or reviewing a generated persona README. Keep it out of the
generated persona's ordinary runtime routes. It is a short editorial step within the
existing production/completion pass, with no new source hunt, planning agent, evidence
schema or recognition round.

## Prepare from the supported perspective

Inspect the existing README, core, reconstruction scope at
`transworld-identity/scope.md`, frameworks, voice and relevant evidence
modules. Identify what draws this perspective's attention, what it asks the reader
to do, and what makes that interaction particular. Trace substantive character claims
through existing evidence links; do not duplicate the recognition profile. A narrow
record calls for a well-written narrow characterization, not invented biography.

Choose a realistic starting situation within the supported use. Include useful friction
where supported: asking for an example, resisting a comforting verdict, noticing an
overlooked constraint, or questioning the terms of the question. Friction is not
compulsory confrontation. Reserve, intensity, patience, humor and exuberance can each
convey presence. Do not impose a friendly tutor voice, generic warmth, catchphrases,
fabricated memories, endorsements or first-person impersonation. Third person, direct
address and restrained editorial narration are all available.

## Give the reader a way in

Introduce whose perspective this is and what thinking with it could be like before a
long inventory or assessment explanation. Show concerns through something the reader
can imagine it doing. Offer a concrete first question, task or situation; no mandatory
dialogue formula. Explain practical uses through what readers bring and what happens
to that material. Keep installation findable and sufficient for the actual host.

Introduction, first interaction, practical use/installation, scope, then status/evidence
is a useful default hierarchy, not a heading order or word quota. The opening should
make sense without knowing Persona Distiller, runtime routing or model endpoints.
Keep material source/scope limitations beside the promises they qualify, including
near the opening when necessary. Never bury them in a collapsed section or replace
them with an unexplained experimental label.

Translate status into consequences without changing it. If recognition has not run,
say so; retain the actual Candidate status. An unavailable endpoint or exhausted call
allowance belongs in the linked assessment record. Readers need to know what remains
unassessed. Keep source limitations that affect quotations beside quotation promises.
Do not repeat the same qualification across every section without a distinct purpose.
Build history, model settings, calls and protocols belong in linked maintainer records,
usually `transworld-identity/`. Editorial quality cannot confer Standard acceptance or
renew historical results. Do not copy the completion report into the opening.

## Preserve and selectively recover

Before an upgrade, inspect introductions, examples, useful questions and narrator.
Classify relevant passages as preserve, qualify, replace or remove; briefly record
why in existing migration/provenance notes. Keep effective prose through directory,
metadata, status and evaluation-protocol changes. Edit only the passages whose support
or scope changed. Preserve unrelated user edits and the existing README language
unless the user requests a language change.

When earlier migrations flattened the prose, inspect available local history or
supplied earlier versions. Recover useful passages selectively against current evidence
and scope, retaining current installation and truthful status. Do not restore an old
README wholesale. If no earlier version is available, write from supported current
material; do not claim to have recovered the original voice.

## Keep examples identifiable

- **Suggested user prompt:** label it as something the reader can try; no observed
  response is implied.
- **Editorial illustration:** label an invented scene or exchange locally and briefly.
  It is neither a historical quotation nor a verified package output. Do not use
  quotation styling that silently attributes invented dialogue to the person.
- **Saved package output:** give actual provenance and version applicability. Do not
  silently edit it and call the result observed behavior; label adaptations separately.
- **Historical quotation:** provide defensible attribution and a source locator.
  If the available edition cannot support it, paraphrase with appropriate qualification
  or remove the quote.

One local label can establish the kind of example without disclaimers on every sentence.
See [contrasting examples and a reviewed migration](readme-examples.md); these illustrate
editorial decisions, not a template to force onto every person.

## Finish in the existing authoring pass

Answer these four questions with concrete references to the draft in the existing
completion/provenance record:

1. **Particularity:** What makes this opening about this perspective? Would changing
   only the name make it fit almost anyone?
2. **Encounter:** What can the reader imagine it doing with a real question, including
   any characteristic challenge, patience or friction?
3. **Entry:** Is there an actionable starting question or situation and a clear path
   to using the package?
4. **Honesty:** Do promises, examples, source limitations and current status agree
   with the available evidence?

Revise specific weak passages once within this editorial pass. These are judgments,
not numerical personality scores or human validation. No judge agents, comparative
benchmarks, readability targets, adjective counts, mandatory warmth scores or automatic
rewrite loops. Style uncertainty does not trigger another evaluation cycle; material
false claims still need correction or removal.

After assessment, patch status and affected qualifications without regenerating the
README. If a README-only edit leaves all recognition inputs unchanged, preserve current
assessment applicability and make zero new recognition calls. If drafting reveals a
runtime defect, record it and use the existing scoped repair rules; do not silently
expand a README task into a persona rebuild. Mechanical tests can verify byte
preservation, links, hashes and call consumption, not literary quality or human presence.
